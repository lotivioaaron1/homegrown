# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project overview

Homegrown is a Flutter mobile app for a community athletics platform in Legazpi City, Albay, Philippines. It connects athletes, coaches, and organizers — auth/onboarding, event creation, stats tracking, leaderboards, a venue locator, and performance dashboards, all backed by Firebase.

## Commands

Run these from the repository root (`c:\flutter\homegrown`).

```
flutter pub get                      # install dependencies (run after pulling or editing pubspec.yaml)
flutter run                          # run on a connected device/emulator
flutter analyze                      # static analysis (flutter_lints via analysis_options.yaml)
flutter test                         # run all tests
flutter test test/widget_test.dart   # run a single test file
flutter build apk                    # Android release build
flutter build windows                # Windows desktop build
```

Tests live in `test/`, mirroring `lib/` — `test/utils/`, `test/services/`, `test/models/`, `test/widgets/` and `test/constants/`, plus a handful of older screen tests sitting loose at the top level alongside the original `widget_test.dart` smoke test. Most of them are fast unit tests over the pure helpers in `lib/utils/`, which is the main reason logic worth testing gets pushed into a plain Dart function there rather than left inline in a screen (see [lib/utils/event_recipients.dart](lib/utils/event_recipients.dart) and [lib/utils/event_reminders.dart](lib/utils/event_reminders.dart) for the pattern). Nothing in the suite touches a real Firebase instance. There is no CI config, no custom lint config beyond the default `flutter_lints` set, and no Cursor/Copilot rule files in this repo.

## Architecture

**State management & routing:** GetX (`package:get`) is used throughout — for reactive state (`.obs` / `Rx*` fields on `GetxController`/`GetxService` classes), dependency injection (`Get.put`/`Get.find`), navigation (`Get.offAllNamed`, `Get.toNamed`, etc.), and snackbars (`Get.snackbar`). All routes are declared as named `GetPage`s in [lib/main.dart](lib/main.dart) — add new screens there rather than using ad-hoc `Navigator.push`.

**Startup/auth flow:** [lib/main.dart](lib/main.dart) initializes Firebase, then registers three global singletons via `initialBinding`: `ConnectivityService`, `ThemeController`, `AuthController`. [lib/screens/splash_screen.dart](lib/screens/splash_screen.dart) owns all initial routing logic (not main.dart): it holds a ~2.2s brand moment and resolves the destination *underneath* it rather than after it, so a fast connection waits only for the hold. Resolution checks `FirebaseAuth.instance.currentUser` — logged in resolves a landing route; not logged in checks the `onboarding_complete` flag in `SharedPreferences` to decide between `/login` and showing the onboarding CTA buttons. Both the cold-start path and `AuthController.signInWithEmail` route through the single pure `landingRoute` in [lib/utils/auth_routing.dart](lib/utils/auth_routing.dart) — put any new post-auth routing rule there rather than in either call site, since they previously drifted apart. Email verification *is* enforced: an unverified password account is held on `/verify-email` and cannot reach the app. Admins bypass this (the role is hand-set in the console, so gating it only risks locking the single admin out), as do Google accounts (no password credential means the verification screen's only action would be a dead end). This is an in-app gate for UX, not a security boundary — a script with the same credentials bypasses it, which is why contact details are protected by data layout instead (see below).

**Layering:** `controllers/` (GetX controllers holding reactive UI state) call into `services/` (stateless wrappers around Firebase/plugin SDKs) which read/write `models/` (plain Dart classes with `toMap`/`fromMap`, no codegen). Screens under `screens/<feature>/` consume controllers via `Get.find()` / `ControllerName.to` and should not call Firebase SDKs directly. Services are intentionally split by Firebase product even when domains overlap, e.g. `StorageService` (single profile avatar in Firebase Storage) is kept separate from `MediaService` (portfolio photos/videos, also Storage + Firestore) — follow this precedent rather than merging storage logic into one class.

**Firebase:** Firestore is the primary datastore; `firebase_options.dart` and `firebase.json` are generated by FlutterFire CLI (project `homegrown-app-b71d1`) — don't hand-edit them. Auth supports email/password and Google Sign-In (`AuthController.signInWithGoogle` creates a minimal Firestore user doc with an empty `role` on first sign-in and returns `null` so the caller routes to role selection).

**User PII:** a `users/{uid}` document is readable by *every* signed-in account, because leaderboards, Scout, rosters and profile sheets all legitimately show a stranger's name, role, sport and barangay. Firestore read rules are document-level, so there is no way to serve some fields and withhold others — contact details therefore live in `users/{uid}/private/contact` (owner and super-admin only) and are read and written exclusively through [lib/services/contact_service.dart](lib/services/contact_service.dart). **Never put `email`, `phoneNumber`, or anything else private back on the profile document**; anything added there is visible to the whole signed-in population. `ContactService.read` still falls back to the legacy top-level fields for accounts that predate the split; that fallback can be dropped once `functions/scripts/migrate-contact-pii.js` has been run with `--delete-legacy`.

**Theming:** [lib/theme/app_theme.dart](lib/theme/app_theme.dart) defines a single `AppTheme` class with `lightTheme`/`darkTheme` `ThemeData` plus semantic color *getters* (`AppTheme.bg`, `.card`, `.textPrimary`, `.sub`, etc.) that switch on `Get.isDarkMode` — use these getters in new UI rather than hardcoding colors, so screens stay theme-aware. `ThemeController` persists the user's light/dark preference to `SharedPreferences` and applies it via `Get.changeTheme`/`Get.changeThemeMode`. The brand color is gold (`#FFB800`).

The one place that ignores the theme is the launch sequence, which is a fixed dark scene end to end. `#07070C` ("ink") is repeated in four places that must stay in step or a colour seam appears mid-launch: `@color/splash_background` (Android's own launch screen, set in *both* `values/styles.xml` and `values-night/styles.xml` — values-night replaces the base style rather than merging with it), `@color/ic_launcher_background` (the adaptive icon's plate), and `_kInk` in [lib/screens/splash_screen.dart](lib/screens/splash_screen.dart). The Android 12+ launch icon is `drawable/splash_icon.xml`, which insets `drawable-nodpi/hg_splash_mark.png` — a **manual byte copy** of `assets/launcher_icon/foreground.png`, taken at 1024px because the system otherwise upscales the 432px launcher layer and the mark looks blurred. Nothing copies it at build time, so re-run `tool/generate_launcher_icons.dart` *and* re-copy that file if the monogram ever changes.

**Connectivity:** `ConnectivityService` (a `GetxService`) combines `connectivity_plus` with a real DNS lookup (adapter-level "connected" isn't the same as internet access) and exposes `isConnected` as an `RxBool`. [lib/widgets/no_internet_overlay.dart](lib/widgets/no_internet_overlay.dart) wraps the whole app (via `GetMaterialApp.builder`) to show an offline overlay reactively — don't build separate per-screen offline banners.

**Event reminders:** Every other notification in the app is a Firestore document written client-side at the moment someone acts (`NotificationService`, rendered in the bell on the home screen). "Your game starts soon" is the one exception, and it is deliberately **not** a Firestore notification: [lib/services/event_reminder_service.dart](lib/services/event_reminder_service.dart) hands the OS scheduled local notifications via `flutter_local_notifications`, so the reminder arrives with the app closed without needing Cloud Functions, FCM or a billing plan. An `event_reminder` document would have to be written either at the reminder moment (which needs the app running, defeating the point) or hours early at schedule time (which would put a "starting soon" row in the bell while it is still untrue) — which is why `NotificationType.eventReminder` exists in the enum but is not in `NotificationService.kTypes` or the `firestore.rules` allowlist, and must not be added. Timing lives in the pure, unit-tested [lib/utils/event_reminders.dart](lib/utils/event_reminders.dart) (18:00 the evening before, plus one hour before kickoff). `syncFor` is called from `HomeScreen.initState` and cancels and rebuilds the whole schedule each time, so a moved or cancelled event needs no bookkeeping; the cost is that reminders only refresh while the app is open. Scheduling is inexact on purpose so `SCHEDULE_EXACT_ALARM` is never needed, the timezone is pinned to `Asia/Manila` rather than adding a package to rediscover a constant, and the service no-ops off Android/iOS so the Windows build is unaffected. The Android side needs core library desugaring in `android/app/build.gradle.kts` plus the two receivers in `AndroidManifest.xml` — without the receivers a reminder is accepted silently and never shown.

**Domain data:** Static reference data lives in `lib/constants/` as plain Dart `const` values, not fetched from Firestore. Venue data is a deliberate exception: it's sourced live via `PlacesService` ([lib/services/places_service.dart](lib/services/places_service.dart), wrapping Google's Places API) when an organizer creates an event, with a manual map-pin fallback (`VenueMapPickerScreen`, using `GeocodingService` for reverse-geocoding) for venues Google doesn't index. This replaced an earlier hand-typed `kLegazpiVenues` list whose guessed coordinates proved unreliable in practice (a mid-city venue was off by hundreds of meters, and free-text geocoding of small local venues by name produced results hundreds of kilometers wrong).

**Users/roles:** Three public roles — `athlete`, `coach`, `organizer` — set at registration (or afterward via `/google-profile-setup` for Google sign-ins). Role-specific registration screens live under `lib/screens/auth/` (`athlete_register_screen.dart`, `coach_register_screen.dart`, `organizer_register_screen.dart`) alongside the shared `register_screen.dart` role picker.

There is a fourth role, `admin` (the super-admin). It is never reachable through the app — `firestore.rules` excludes `'admin'` from both the role allowlist on create and the one role-change branch on update, so an admin account exists only because someone hand-set the field in the Firestore console. An admin lands on `/admin` → `AdminShellScreen` ([lib/screens/admin/admin_shell_screen.dart](lib/screens/admin/admin_shell_screen.dart)), a five-tab console: Overview, Users, Content, Reports, Approvals. Admin identity is checked two different ways and both must be kept in step — `firestore.rules` does a live `role == 'admin'` lookup via `isAdmin()`, while `storage.rules` compares against a hardcoded UID list in `isAdminUid()` (a cross-service `firestore.get()` from Storage rules returns `unauthorized` in this project), so provisioning a second admin means editing and redeploying `storage.rules` too.

**What an admin may write** is deliberately narrow, and the security rules — not the UI — are the boundary. Across another user's document an admin can change exactly two things: `organizerStatus` (the approval queue) and the suspension trio `suspended` / `suspendedAt` / `suspendedReason` ([lib/services/admin_user_service.dart](lib/services/admin_user_service.dart)). On content they can change only `status` on an `events` or `tournaments` document, which in practice means cancelling. Everything else — roles, profile fields, stats, another user's notifications or rating history — is denied to an admin exactly as it is to anyone else. Add a capability by adding a matching field-restricted rule, not by widening an existing one.

**Suspension** is an in-app gate, not a security boundary, in the same way the email-verification gate is: `landingRoute` in [lib/utils/auth_routing.dart](lib/utils/auth_routing.dart) holds a suspended non-admin on `/suspended`, but a script with the same credentials still reads and writes whatever the rules allow. Enforcing it in the rules would add a `get()` on the user document to every write in the app. Admins are exempt from the gate on purpose — lifting a suspension happens inside the console, so a suspended admin could never reach the screen that would undo it. There is **no admin-side account deletion**: without Cloud Functions the app cannot remove a Firebase Auth account, and deleting only the Firestore document would leave a working login attached to nothing. Real removal stays an operator task via `functions/scripts/purge-orphaned-profiles.js`.

**Reports** (`reports/{reportId}`, [lib/models/report.dart](lib/models/report.dart)) are filed from a shared sheet, `showReportDialog` in [lib/widgets/report_dialog.dart](lib/widgets/report_dialog.dart) — call that rather than building a form, and pass a new `targetType` to cover a new kind of target. The collection is effectively write-only for ordinary users: they can create a report attributed to themselves and read back only their own, so nobody but the admin can see the queue or learn who reported whom.
