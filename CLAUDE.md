## Project overview

Homegrown is a Flutter mobile app for a community athletics platform in Legazpi City, Albay, Philippines. It connects athletes, coaches, and organizers — auth/onboarding, event creation, stats tracking, leaderboards, a venue locator, and performance dashboards, all backed by Firebase.

## Commands

Run these from the repository root (`c:\flutter\homegrown`).

```
flutter pub get                      # install dependencies (run after pulling or editing pubspec.yaml)
flutter run                          # run on a connected device/emulator
flutter analyze                      # static analysis (flutter_lints via analysis_options.yaml)
flutter test                         # run all tests
flutter test test/widget_test.dart   # run a single test file
flutter build apk                    # Android release build
flutter build windows                # Windows desktop build
```

There is only one test file (`test/widget_test.dart`), a basic smoke test. There is no CI config, custom lint config beyond the default `flutter_lints` set, and no Cursor/Copilot rule files in this repo.

## Architecture

**State management & routing:** GetX (`package:get`) is used throughout — for reactive state (`.obs` / `Rx*` fields on `GetxController`/`GetxService` classes), dependency injection (`Get.put`/`Get.find`), navigation (`Get.offAllNamed`, `Get.toNamed`, etc.), and snackbars (`Get.snackbar`). All routes are declared as named `GetPage`s in [lib/main.dart](lib/main.dart) — add new screens there rather than using ad-hoc `Navigator.push`.

**Startup/auth flow:** [lib/main.dart](lib/main.dart) initializes Firebase, then registers three global singletons via `initialBinding`: `ConnectivityService`, `ThemeController`, `AuthController`. [lib/screens/splash_screen.dart](lib/screens/splash_screen.dart) owns all initial routing logic (not main.dart): it always shows the splash animation for 2.5s, then checks `FirebaseAuth.instance.currentUser` — logged in resolves a landing route; not logged in checks the `onboarding_complete` flag in `SharedPreferences` to decide between `/login` and showing the onboarding CTA buttons. Both the cold-start path and `AuthController.signInWithEmail` route through the single pure `landingRoute` in [lib/utils/auth_routing.dart](lib/utils/auth_routing.dart) — put any new post-auth routing rule there rather than in either call site, since they previously drifted apart. Email verification *is* enforced: an unverified password account is held on `/verify-email` and cannot reach the app. Admins bypass this (the role is hand-set in the console, so gating it only risks locking the single admin out), as do Google accounts (no password credential means the verification screen's only action would be a dead end). This is an in-app gate for UX, not a security boundary — a script with the same credentials bypasses it, which is why contact details are protected by data layout instead (see below).

**Layering:** `controllers/` (GetX controllers holding reactive UI state) call into `services/` (stateless wrappers around Firebase/plugin SDKs) which read/write `models/` (plain Dart classes with `toMap`/`fromMap`, no codegen). Screens under `screens/<feature>/` consume controllers via `Get.find()` / `ControllerName.to` and should not call Firebase SDKs directly. Services are intentionally split by Firebase product even when domains overlap, e.g. `StorageService` (single profile avatar in Firebase Storage) is kept separate from `MediaService` (portfolio photos/videos, also Storage + Firestore) — follow this precedent rather than merging storage logic into one class.

**Firebase:** Firestore is the primary datastore; `firebase_options.dart` and `firebase.json` are generated by FlutterFire CLI (project `homegrown-app-b71d1`) — don't hand-edit them. Auth supports email/password and Google Sign-In (`AuthController.signInWithGoogle` creates a minimal Firestore user doc with an empty `role` on first sign-in and returns `null` so the caller routes to role selection).

**User PII:** a `users/{uid}` document is readable by *every* signed-in account, because leaderboards, Scout, rosters and profile sheets all legitimately show a stranger's name, role, sport and barangay. Firestore read rules are document-level, so there is no way to serve some fields and withhold others — contact details therefore live in `users/{uid}/private/contact` (owner and super-admin only) and are read and written exclusively through [lib/services/contact_service.dart](lib/services/contact_service.dart). **Never put `email`, `phoneNumber`, or anything else private back on the profile document**; anything added there is visible to the whole signed-in population. `ContactService.read` still falls back to the legacy top-level fields for accounts that predate the split; that fallback can be dropped once `functions/scripts/migrate-contact-pii.js` has been run with `--delete-legacy`.

**Theming:** [lib/theme/app_theme.dart](lib/theme/app_theme.dart) defines a single `AppTheme` class with `lightTheme`/`darkTheme` `ThemeData` plus semantic color *getters* (`AppTheme.bg`, `.card`, `.textPrimary`, `.sub`, etc.) that switch on `Get.isDarkMode` — use these getters in new UI rather than hardcoding colors, so screens stay theme-aware. `ThemeController` persists the user's light/dark preference to `SharedPreferences` and applies it via `Get.changeTheme`/`Get.changeThemeMode`. The brand color is gold (`#FFB800`).

**Connectivity:** `ConnectivityService` (a `GetxService`) combines `connectivity_plus` with a real DNS lookup (adapter-level "connected" isn't the same as internet access) and exposes `isConnected` as an `RxBool`. [lib/widgets/no_internet_overlay.dart](lib/widgets/no_internet_overlay.dart) wraps the whole app (via `GetMaterialApp.builder`) to show an offline overlay reactively — don't build separate per-screen offline banners.

**Domain data:** Static reference data lives in `lib/constants/` as plain Dart `const` values, not fetched from Firestore. Venue data is a deliberate exception: it's sourced live via `PlacesService` ([lib/services/places_service.dart](lib/services/places_service.dart), wrapping Google's Places API) when an organizer creates an event, with a manual map-pin fallback (`VenueMapPickerScreen`, using `GeocodingService` for reverse-geocoding) for venues Google doesn't index. This replaced an earlier hand-typed `kLegazpiVenues` list whose guessed coordinates proved unreliable in practice (a mid-city venue was off by hundreds of meters, and free-text geocoding of small local venues by name produced results hundreds of kilometers wrong).

**Users/roles:** Three roles — `athlete`, `coach`, `organizer` — set at registration (or afterward via `/google-profile-setup` for Google sign-ins). Role-specific registration screens live under `lib/screens/auth/` (`athlete_register_screen.dart`, `coach_register_screen.dart`, `organizer_register_screen.dart`) alongside the shared `register_screen.dart` role picker.
